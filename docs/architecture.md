# Architecture

vibi exposes YouTube search, video metadata, and transcripts to coding agents. The same behaviour reaches three different agent runtimes — Pi, MCP clients, and anything with JSON function calling — without being reimplemented for each.

This document explains the shape of the system and why it is shaped that way. For the tool contract and adapter-authoring steps, see [`adapters.md`](adapters.md). For vocabulary, see [`../CONTEXT.md`](../CONTEXT.md).

## Goals

1. **One implementation of YouTube behaviour.** Search, metadata, and transcript logic exist once. Adapters only translate.
2. **No agent SDK below the adapter layer.** The domain and tool layers must run in a plain Node process.
3. **Output shaped for a model's context window.** Every response is capped, compacted, and rendered as text a model can act on.
4. **Failures the model can read.** Expected failures are returned as data, not raised as exceptions.

## Layers

```txt
lib/                     capability layer — pure functions + outbound I/O
  youtube-api.ts           YouTube Data API v3 client (search, videos.list)
  transcript.ts            caption fetch, hook/outro extraction, failure classification
  video-id.ts              video input parsing and de-duplication
  formatters.ts            rendering, compaction, truncation
  config.ts                API key resolution and precedence
  auth-store.ts            stored API key file
  errors.ts, schema.ts     shared error types and schema helper

tools/                   agent-neutral tool core — the seam
  types.ts                 YoutubeToolSpec, ToolOutcome, ToolContext
  youtube-tools.ts         the three tool specs: JSON Schema + handler
  index.ts                 registry, executeYoutubeTool(), toJsonSchema()

adapters/                per-agent projection
  pi/                      Pi extension: registerTool() + /youtube:* commands
  mcp/                     MCP stdio server: protocol + transport
  portable.ts              OpenAI / Anthropic / generic JSON tool definitions

extensions/              Pi package entrypoint (re-export of adapters/pi)
bin/                     executable entrypoints (plain JS, imports dist/)
dist/                    compiled JS + .d.ts — generated by `npm run build`
```

Sources are TypeScript, but **`dist/` is the runtime artifact**. See
[Compiled JavaScript is the runtime artifact](#compiled-javascript-is-the-runtime-artifact).

### The dependency rule

```txt
adapters/  →  tools/  →  lib/
```

One direction only. Nothing in `tools/` or `lib/` may import from `adapters/`, and nothing below `adapters/` may import `@earendil-works/*` or any other agent SDK. This is what makes the core portable: if the rule holds, any agent that can express a JSON Schema and call a function can use the tools.

### Why `tools/` exists

The first version of this code kept tool registration, schema declaration, orchestration, and result shaping in one Pi-specific file. That works for exactly one agent. Extracting `tools/` turns the use case into the stable centre of the design and demotes each agent integration to a translation layer.

## The tool contract

```ts
interface ToolOutcome {
  text: string;                      // model-facing text
  data?: Record<string, unknown>;    // structured payload
  isError?: boolean;                 // true when `text` describes a failure
}

interface YoutubeToolSpec<Input> {
  name: string;
  label: string;
  description: string;
  promptSnippet?: string;            // host system-prompt entry
  promptGuidelines?: string[];       // host guidance bullets
  parameters: TSchema;               // JSON Schema
  execute(input: Input, context?: ToolContext): Promise<ToolOutcome>;
}
```

Handlers return text and structured data. They never build SDK content blocks, never stream, and never touch a host UI. Adapters own all of that.

## Design decisions

### Failures are outcomes, not exceptions

Handlers catch expected failures and return `isError: true` with explanatory text. The Pi adapter forwards that text as a normal tool result; the MCP adapter additionally sets `isError` on the result. Only genuinely unexpected errors escape a handler, and the dispatcher converts those too.

The reason is behavioural: an agent that receives a readable failure can retry with a different language, pick a different video, or tell the user what is wrong. An exception ends the tool call without that context. Transcript failures go further and carry a **transcript diagnostic** — an attempted language, a reason code, and a suggested next action — so the retry does not require guesswork.

### The core returns text, not content blocks

Each protocol has its own result envelope: Pi wants `{ content: [...], details }`, MCP wants `{ content: [...], isError, structuredContent }`, an OpenAI-style loop wants a raw string. Returning a neutral `{ text, data }` keeps the core ignorant of all three.

### `excerpt`, not `key_segments`

The `youtube_transcript` format value is `excerpt`. The old name promised caption *segments*, but the payload is two text windows — a name/value mismatch that made every reader check the implementation. "Transcript" already means the timed segment sequence, so the derived artifact needed its own word.

### `data`, not `details` or `response`

`ToolOutcome.data` holds the structured payload. `details` was rejected because it collides with the project's `VideoDetails` domain object. `response` was rejected because it names a whole reply while this field is only the non-text part of one, and because `outcome.response` reads circularly.

Pi maps `data` onto its own `details` field and MCP maps it onto `structuredContent`; the neutral name never leaks into a protocol.

### Key commands are namespaced, with a read-only default

Credential commands live under `/youtube:key`: the bare command reports status, `/youtube:key:set` stores a key, and `/youtube:key:clear` removes it. The earlier `login`/`logout` pair implied a session that does not exist — nothing is logged into, a key is stored — and `login` collided with Pi's own `/login`, which configures provider authentication. The names follow the glossary term **API key source**, and mutations require an explicit verb so the bare command is always safe to run.

### Compiled JavaScript is the runtime artifact

Node refuses to strip TypeScript types for files under `node_modules`
(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), so a package that ships only
`.ts` files cannot be imported or executed by a plain Node.js process once
installed. Everything that runs outside Pi therefore points at compiled output:
the `bin` entry, and the `exports` map.

Pi is the exception. Pi loads extensions through its own transpiler, which reads
the TypeScript sources directly, so `pi.extensions` keeps pointing at
`extensions/` and `pi -e .` works from a fresh checkout with no build.

`npm run build` (`tsc -p tsconfig.build.json`) emits JS to `dist/`.
`rewriteRelativeImportExtensions` turns the `./foo.ts` specifiers used in source
into `./foo.js` in the output, so there is one import style in the repository and
another only in generated code. `prepack` runs the build, so a publish can never
ship a stale `dist/`.

The consequence for the tarball: both the TypeScript sources and `dist/` are
published. The sources exist for Pi and for readers; `dist/` is what executes.

### TypeBox is the schema authoring layer

Tool parameters are authored with TypeBox because its runtime output *is* JSON Schema. Pi receives the schema object directly, and MCP serialises it through `toJsonSchema()`, which strips the non-enumerable TypeBox marker. One schema definition serves every adapter with no conversion table to maintain.

### Tool names stay `youtube_*`

`vibi` is the project; `youtube_*` describes the capability. A model choosing a tool needs to know what the tool does, not what the package is called.

## Context shaping

Agent context is the scarcest resource in the design, so formatting is treated as a first-class concern rather than left to each adapter:

- Search results are compacted and capped, with the result count clamped to a small range.
- Descriptions are truncated only when explicitly requested, and the truncation limit appears in the tool schema description so the model knows the cap before paying for it.
- Transcripts default to an excerpt (hook + outro) because the opening and closing windows are usually enough to orient a model, and full text is an order of magnitude larger.
- Every rendered response passes through an output guard that appends a `[truncated N chars]` marker, so a model can tell the difference between "the video is short" and "the answer was cut".

Limits live as exported constants in `lib/formatters.ts` and `lib/transcript.ts`; the user-facing summary is in the [README](../README.md#output-guards).

## Authentication

One resolution path, shared by every adapter:

1. `YOUTUBE_API_KEY` — for CI, containers, and MCP client configs.
2. `~/.pi/agent/vibi-auth.json` (mode 600) — written by `/youtube:key:set`, for interactive Pi use.

The precedence lives in `lib/config.ts`. `authStatusText()` reports only the source, never the key, so it is safe to surface in a UI or a log line. The MCP adapter needs no auth machinery of its own: it picks up the environment variable, or the same stored file when it runs on the same machine as Pi.

The split between `config.ts` (resolution) and `auth-store.ts` (file access) keeps the policy testable without touching a filesystem.

## Testing

Tests run on `node --test` with no framework. The layers are tested differently:

| Layer | Approach |
|---|---|
| `lib/` | Direct unit tests. The YouTube client and transcript fetcher accept injected `fetchFn` / `fetcher`, so no network is required. |
| `tools/` | Contract tests: tool roster, JSON Schema serialisability, dispatcher error paths. Network-free by construction — the failure paths need no API key. |
| `adapters/pi` | A fake `pi` object captures registrations and invokes `execute`. |
| `adapters/mcp` | `handleMessage()` is driven directly for protocol cases, and `bin/mcp.mjs` is spawned once to prove the transport and entrypoint work. |

Auth tests point `PI_YOUTUBE_AGENT_DIR` at a temp directory, so a developer's real stored key is never read or written.

## Extending

A new agent integration is a single file that reads `youtubeTools`, maps `parameters` to the host's schema format, and maps `ToolOutcome` to the host's result shape. Step-by-step instructions and a skeleton are in [`adapters.md`](adapters.md).

The rule for keeping the seam intact: if you find yourself formatting an API response, resolving an API key, or classifying a failure inside an adapter, that code belongs in `tools/` or `lib/` instead.
